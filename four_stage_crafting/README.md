> 🚀 **时代定位**: AI时代软件研发的精工激发引擎 - 基于文档系统复杂度六维度模型的核心生产力工具
> 
> 📖 **核心使命**: 在AI Coding时代，将文档从辅助工具升级为核心生产资产，通过精工策略激发确保AI理解准确、代码质量优秀

## 📖 核心术语定义

### 🎯 关键概念说明
- **Stage**: 四个开发阶段 - REQUIREMENTS(需求)、DESIGN(设计)、IMPLEMENTATION(实施)、TASK_PLANNING(任务规划)
- **CRAFT**: 精工指导文档，每个Stage在每个Level都有对应的精工策略文档
- **Level**: 三个复杂度级别 - L1-STREAMLINED(快速)、L2-BALANCED(平衡)、L3-RIGOROUS(严格)
- **六维度模型**: 文档系统复杂度的六个控制维度 - 文档组织、目录层级、分类粒度、关联复杂度、内容深度、形式化程度
- **精工激发者**: four_stage_crafting体系的角色定位，负责提供"如何做得更好"的创意策略
- **约束守门员**: four_stage_constraints体系的角色定位，负责定义"什么是可接受的"验收标准

### 🏷️ CRAFT XML标记体系术语
- **MD+XML混合架构**: 保持专家友好的Markdown主干 + LLM友好的XML标记
- **XML标记**: 格式为 `<craft-[stage]-req[1-4]-[level]>`，如 `<craft-requirements-req1-l1>`
- **子标签**: XML标记内的具体内容标签，分为6个维度标签和专项标签两类
- **主攻维度**: 各阶段的核心维度，内容最详细充实
- **Level间切换**: L1/L2/L3使用相同XML结构，仅内容复杂度不同，支持无缝替换

### 🎭 角色术语说明
- **PM** (Product Manager): 产品经理
- **BA** (Business Analyst): 业务分析师  
- **Dev** (Developer): 开发人员
- **Test** (Tester): 测试人员
- **Ops** (Operations): 运维人员
- **管理层** (Management): 项目管理层

## 🎯 AI时代的精工理念

### 基于六维度模型的精工策略

#### 核心认知：文档系统决定AI输出质量
```markdown
文档系统六维度 → AI理解精度 → 代码生产质量
     ↓                ↓             ↓
维度优化策略        智能解析      质量保证机制
精工激发方法        上下文理解    持续改进循环
```

#### 精工 vs 约束的AI时代分工
```markdown
约束守门员 (four_stage_constraints/):
- 定义AI理解的基础规范和质量底线
- 规定"不能做什么"，防范AI理解偏差
- 确保文档符合机器可读的标准格式

精工激发者 (four_stage_crafting/):  
- 激发六维度精工方法和创意策略
- 指导"如何做得更好"，提升AI理解精度
- 促进跨级别优化，持续提升文档系统质量
```

### 🤝 多角色协作约束原则

> 💡 **核心理念**: 精工策略必须服务多角色协作，确保PM/BA/Dev/Test/Ops/管理层都能理解和参与

#### 📋 核心约束标准
- **🚫 避免过度技术化**: 代码片段不应占据大量内容，技术细节应适度包装和解释
- **💼 业务导向优先**: 优先描述业务价值、用户场景、验收标准，技术细节为业务服务
- **🗣️ 通用术语表达**: 使用各角色都能理解的通用术语和表达方式
- **📊 结构清晰可读**: 采用清晰的标题、列表、表格等结构化表达，便于快速理解

### 🚀 AI时代的精工驱动战略

**核心战略**: AI生产 + Human精工 + 多角色协作 = 从合规基础到精工优秀的完美跃升

**双阶段协同模式**:
- **AI生产阶段**: 基于约束标准建立合规文档基础，同时嵌入精工激发策略和多角色协作约束
- **Human推敲阶段**: 在约束边界内激发创意优化，各角色协作参与，实现跨级别精工跃升

### 适应性精工策略：六维度配置差异化

#### 🎯 三级别精工策略（基于思考维度优先原则）

> 💭 **思考维度优先原则**: L1/L2/L3的差异本质体现在思考维度的深度和广度，而非团队规模或项目类型。每个级别都适用于任意规模团队，区别在于用户对质量控制的偏好程度。

| 级别 | 用户偏好特征 | 核心价值 | 思考维度特征 |
|------|----------|----------|-------------|
| **L1-STREAMLINED** | 快速迭代偏好，容忍合理妥协的任意规模团队 | 信息密度优化，聚焦核心价值交付 | 核心维度思考，快速决策 |
| **L2-BALANCED** | 标准流程偏好，平衡质量效率的任意规模团队 | 平衡全面性与效率，支持协作理解 | 标准维度思考，结构化决策 |
| **L3-RIGOROUS** | 严格控制偏好，完整决策追溯的任意规模团队 | 完整性和规范性，确保完整追溯 | 深度维度思考，追溯完整性 |

## 🔧 CRAFT XML标记体系技术实现

### 📊 统一XML标记结构

#### 核心设计约束
- **48个XML标记**: 4阶段 × 3级别 × 4要求 = 48个标记统一管理
- **42种子标签类型**: 6个维度子标签 + 36个专项子标签 = 完整覆盖
- **Level间内容固化**: L1/L2/L3使用相同子标签结构，在生产时确定具体级别内容

#### 最终维度结构映射表
```
REQUIREMENTS:   需求精研_要求1_文档体系 → 需求精研_要求2_需求格式 → 需求精研_要求3_验收标准 → 需求精研_要求4_质量标准
DESIGN:         精工设计_要求1_文档体系 → 精工设计_要求2_架构表达 → 精工设计_要求3_技术决策 → 精工设计_要求4_质量标准
IMPLEMENTATION: 实施精策_要求1_文档体系 → 实施精策_要求2_TDD深度 → 实施精策_要求3_任务颗粒度 → 实施精策_要求4_质量标准
TASK_PLANNING:  任务精控_要求1_文档体系 → 任务精控_要求2_策略规划 → 任务精控_要求3_验证跟踪 → 任务精控_要求4_质量标准
```

**统一约束**:
- **要求1**: 所有阶段都是"文档体系"，使用相同的6个子标签维度
- **要求2-4**: 体现各阶段专业特色（需求格式、架构表达、TDD深度、策略规划等）
- **Level一致性**: 相同标签名在L1/L2/L3中结构相同，内容复杂度递进

#### XML标签命名规范
```xml
<!-- 标准格式 -->
<craft-[stage]-req[1-4]-[level]>

<!-- 具体示例 -->
<craft-requirements-req1-l1>     <!-- 需求阶段要求1 L1级别 -->
<craft-design-req2-l2>           <!-- 设计阶段要求2 L2级别 -->
<craft-implementation-req3-l3>   <!-- 实施阶段要求3 L3级别 -->
<craft-task-planning-req4-l1>    <!-- 任务规划阶段要求4 L1级别 -->
```

### 🎯 六维度模型XML标签约束

#### 要求1_文档体系：6个统一维度子标签（所有阶段通用）
```xml
<craft-[stage]-req1-[level]>
<document-organization>[L级别]文档组织策略和控制原则</document-organization>
<directory-hierarchy>[L级别]目录层级组织和导航结构（IMPLEMENTATION主攻）</directory-hierarchy>
<categorization-granularity>[L级别]分类粒度策略（REQUIREMENTS主攻）</categorization-granularity>
<interconnection-complexity>[L级别]关联复杂度管理（DESIGN主攻）</interconnection-complexity>
```
