### ⚡ LLM策略要点速查
#### 🚫 严禁行为
- 绝不在没有需求文档情况下开始设计
- 不跳过深度技术调研直接选择方案
- 不编写具体测试用例或实施TDD
- 不简化架构设计，避免跳过严格分层

#### ✅ 必须规划
- 基于已批准的requirements/交付物进行设计
- **Layer优先架构**：严格分层设计，层次边界清晰，契约优先
- **严格架构要求**：详细架构图，完整组件体系，支持高质量扩展
- **严格技术评估**：完整风险分析，长期维护性优先
- 严格研究流程：领域识别→深度调研→多方案对比→风险评估→决策记录
- 详尽7部分结构+ADR：概述→架构→组件→数据→错误→测试→决策记录
- **形式化流程**：完整架构决策记录，支持第三方审计
- 必须询问："设计看起来可以吗？如果可以，我们可以继续制定实施计划。"

## 🧪 TDD在设计阶段的正确定位

**核心原则**：可测试性设计，为TDD做准备（但不实施TDD）

```
TDD在设计阶段的职责边界：
✅ 应该做：严格可测试架构设计，支持严格测试金字塔(70%单元+20%集成+10%E2E)
✅ 应该做：严格TDD预备架构，为严格TDD红绿重构循环做准备（但不实施）
✅ 应该做：基于严格组件责任边界提供完整技术基础
✅ 应该做：严格数据模型设计和领域模型设计
❌ 不应做：编写具体测试用例
❌ 不应做：进行测试驱动开发
❌ 不应做：实施TDD的红绿重构循环
```

**价值体现**：为实施规划(Implementation)阶段（TDD真正主场）提供严格的技术架构基础

## 🎯 L3约束检查重点

### 哼将产出验收标准

> **"哼哈二将"角色分离说明**：在本框架中，CRAFT负责实际内容生产（"哼将"），CONSTRAINT负责质量检查验收（"哈将"）。本文档作为"哈将"，专门验收CRAFT生产的内容质量。

**验收CRAFT生产的设计文档符合L3-RIGOROUS标准：**

- **严格性验证**: 确保输出符合严格控制要求，支持第三方技术审计
- **Layer-first架构验证**: 检查架构严格分层设计，层次边界清晰，采用Layer-first设计原则
- **DES测试资产载体构建验证**: 验证DES作为L3测试资产载体，为下游IMPLEMENTATION阶段提供设计驱动测试基础
- **严格架构验证**: 验证详细架构图，完整组件体系，支持高质量扩展
- **契约优先验证**: 检查接口契约完整性，支持形式化验证
- **技术评估严格性**: 验证深度技术调研、多方案对比和完整风险评估
- **决策记录完整性**: 检查ADR决策记录完整，支持技术审计
- **完整性检查**: 验证严格架构设计和完整技术方案体系
- **边界合规性**: 检查严格避免TDD实施，维护设计阶段职责边界
- **格式规范性**: 验证使用详尽7部分结构+ADR决策记录
- **可审计性**: 验证完整技术决策记录和设计追溯体系
- **质量控制**: 验证严格的质量标准和完整性要求
- **架构严谨性**: 检查形式化架构模式和高质量扩展支持
- **技术术语密度验证**: 验证技术术语密度 ≤ 20%，80%业务语言表达
- **业务上下文验证**: 检查所有技术概念都有业务理由说明和追溯依据
- **过程式代码禁止验证**: 确保示例不含函数调用、API方法等过程式代码
- **L3追溯链条验证**: 检查设计文档与需求的追溯关系(US→DES→CMP/API)
- **审计人员可读性验证**: 验证审计人员能理解技术选型的业务理由
- **L3审计元数据完整性验证**: 验证所有DES/ADR/CMP/API制品包含完整审计字段（owner+version+timestamp）
- **完整记录验证**: 检查所有决策点都有完整记录和审核依据，audit_log_ref字段关联完整

## 📋 验收执行协议 ⭐ AI强制执行指南

> **目的**: Task-S4-4必须输出结构化验收报告，包含：验收对象清单、逐项检查结果（✅/❌+具体证据）、通过率统计、失败项详单、验收结论。
> 
> **L3特征**: 验收项最多（18项）、标准最严格，需检查Layer优先架构、ADR决策记录、审计追溯、文档数量=11。
> 
> **L3数值标准**: 检查点数量=18项，通过率阈值≥95%，追溯深度≥3层（US→DES→CMP/API→SC多层追溯+ADR双向追溯）
> 
> **DESIGN特殊性**: 需验收artrifact格式、追溯链、端到端价值映射等DESIGN特有内容。

### 🔴 强制验收项（L3-RIGOROUS标准）- 分3组共18项

#### 第1组：格式与追溯验收（4项）

##### 1. Technical Acceptance格式验收
- 每个TAC必须包含Front Matter（id: TAC-<SN>-NNN + sn: <SN> + source_us: US-<SN>-NNN）
- TAC验收US的技术实现路径
- L3额外要求：TAC包含形式化验收标准、审计依据

##### 2. Function Point格式验收
- 每个FP必须包含Front Matter（id: FP-<SN>-NNN + sn: <SN> + source_us: US-<SN>-NNN）
- FP包含技术架构映射
- L3额外要求：FP包含契约优先设计、完整边界定义

##### 3. 追溯链完整性验收
- US→TAC→FP追溯链完整
- SN字段跨文档一致
- L3额外要求：双向追溯、支持第三方审计

##### 4. 文档维度完整性验收 ⭐ 新增
- **L3核心维度标准**: 必须覆盖11个专业维度
  - 维度1: Vertical Slices（端到端切片维度）- 必需
  - 维度2: Technical Acceptance（技术验收维度）- 必需
  - 维度3: Architecture（架构设计维度）- 必需（L3多视图架构）
  - 维度4: API Design（接口设计维度）- 必需
  - 维度5: Data Model（数据模型维度）- 必需
  - 维度6: Component Design（组件设计维度）- 必需
  - 维度7: Interface Contracts（接口契约维度）- 必需（L3契约优先）
  - 维度8: Deployment Design（部署设计维度）- 必需（L3运维）
  - 维度9: Security Design（安全设计维度）- 必需（L3安全）
  - 维度10: Performance Design（性能设计维度）- 必需（L3性能）
  - 维度11: ADR Records（架构决策记录维度）- 必需（L3审计）
- **维度覆盖验收**: 11个核心维度必须覆盖
- **检查方法**:
  - 步骤1: 确认11个核心维度必须覆盖（每个维度至少有对应文档体现）
  - 步骤2: 确认CRAFT_L3_DESIGN.md体现维度驱动原则（维度是核心，文件数量是反映）
- **失败案例**:
  - "11个vertical_slices文件" → 缺少其他10个维度覆盖
  - "6个US + 5个Architecture" → 缺少TAC/API/Data等5个维度覆盖

#### 第2组：架构质量验收（10项）

##### 6. Layer优先架构验收 ⭐ L3特有
- 严格分层设计，层次边界清晰
- 契约优先，形式化接口定义

##### 7. ADR决策记录验收 ⭐ L3特有
- Architecture Decision Records完整
- 所有重要技术决策都有ADR记录
- 决策背景、方案对比、选择理由、风险评估完整

##### 8. 技术选型严格性验收
- 深度技术调研（不只是表面调研）
- 多方案对比分析（至少3个方案）
- 完整风险评估
- 长期维护性优先

##### 9. 可测试性设计验收
- 架构设计支持严格TDD（但不实施TDD）
- 支持严格测试金字塔(70%单元+20%集成+10%E2E)
- 为实施规划阶段提供严格技术基础

##### 10. 审计追溯链验收 ⭐ L3特有
- 设计文档与需求的追溯关系(US→DES→CMP/API)完整
- 支持第三方审计
- 追溯矩阵完整

##### 11. 形式化流程验收 ⭐ L3特有
- 完整架构决策记录
- 支持第三方技术审计
- 决策过程可审计

##### 12. 严格架构验证
- 详细架构图（不只是概念图）
- 完整组件体系
- 支持高质量扩展

##### 13. 契约优先验证 ⭐ L3特有
- 接口契约完整性
- 支持形式化验证
- API契约优先于实现

##### 14. 质量控制验收
- 严格的质量标准
- 完整性要求明确

##### 15. 架构严谨性验收
- 形式化架构模式
- 高质量扩展支持

#### 第3组：内容规范验收（3项）

##### 16. 端到端价值映射验收
- 端到端价值链路（前端交互/数据流转/后端处理/结果反馈）清晰
- 价值链路到架构组件的映射完整
- L3额外要求：包含主流程+所有替代路径+异常处理

##### 17. 业务语言比例验收
- 技术术语密度 ≤ 20%
- 80%业务语言表达，PM能理解"做什么"
- L3额外要求：审计人员能理解技术选型的业务理由

##### 18. 禁止过程式代码验收
- 示例不含函数调用（如AuthService.authenticate()）
- 示例不含API方法
- 允许声明式代码（接口契约、数据结构、配置文件）
