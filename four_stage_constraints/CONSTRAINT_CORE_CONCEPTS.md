## 📍 SPEC框架系统边界

> 📌 **核心概念**: SPEC框架工作边界和阶段职责的权威定义，为整个约束体系提供基础认知

### 系统边界定义
**边界本质**: SPEC框架采用严格的阶段性质分离原则，将软件开发过程划分为文档策划与代码执行两个截然不同的工作性质域

```
📋 REQUIREMENTS → 📐 DESIGN → 🧪 IMPLEMENTATION → 📝 TASK_PLANNING → 💻 实际开发阶段
   需求澄清        设计文档      TDD粒度决策       声明式目标        真正写代码执行TDD
   (纯MD文档)     (纯MD文档)    +项目规划        +AI上下文规格      (真正执行)
                               (纯MD文档策略)    (纯MD文档编排)     
```

### 阶段工作性质
**文档策划域(前四阶段)**:
- **📋 REQUIREMENTS**: 业务需求澄清域 - 纯文档策划，确定项目目标和验收标准
- **📐 DESIGN**: 技术设计方案域 - 纯文档策划，确定架构和实现路径
- **🧪 IMPLEMENTATION**: 实施策略规划域 - 纯文档策略，制定TDD粒度决策(unit/integration/e2e)和项目规划
- **📝 TASK_PLANNING**: 任务规划关联复杂度控制域 - 声明式执行目标制定，AI上下文规格制定

**代码执行域(后续阶段)**:
- **💻 实际开发阶段**: 代码实施执行域 - 基于前四阶段文档指导的实际编程和TDD执行

### 边界价值
- **职责域分离**: 通过严格的工作性质划分，确保阶段职责不混淆，维护专业化分工原则
- **AI角色定位**: 为AI在不同性质域中的能力边界和协作模式提供明确的理论框架
- **质量控制基础**: 建立文档策划与代码执行的清晰分离机制，为质量门禁提供架构依据
- **防护理论支撑**: 为编码冲动防护机制提供权威的理论基础和边界划分标准

### 与约束体系的关系
> **📌 基础认知定位**: 系统边界定义为SPEC框架的最基础认知概念，为后续所有约束维度提供工作边界基础

- **支撑二维决策模型**: 明确边界后，用户可在协作模式(C1/C2/C3)和质量控制级别(L1/L2/L3)两个维度上进行精准选择
- **指导文档状态管理**: 基于边界定义，确保文档状态机在正确的工作性质范围内运转
- **约束AI执行视角**: 为LM1/LM2/LM3执行策略提供边界约束和角色定位依据

## 🎯 核心架构理念

### 二维独立决策模型

本框架采用二维独立决策模型，将用户资源和项目需求分离为两个完全独立的决策维度：

1. **协作模式维度**: 
   - 定义：人机对话中的领导权分配和知识贡献模式
   - 决策标准：用户的控制欲望强度、专业知识储备、时间投入意愿
   - 选项：C1-CONFIRM（AI主导）、C3-LEAD（用户主导）、C2-PARTICIPATE（平等协作）

2. **质量控制维度**: 
   - 定义：项目执行的流程复杂度和质量严格程度
   - 决策标准：项目关键程度、协作需求复杂度、合规审计要求、时间压力
   - 选项：L1-STREAMLINED（快速迭代级）、L2-BALANCED（标准流程级）、L3-RIGOROUS（严格控制级）

> 📌 **独立性原则**: 这两个维度在概念上完全独立且可以自由组合。协作模式决定"谁主导和如何交互"，质量控制决定"执行什么标准和多严格"。用户根据项目特点和个人偏好在两个维度上独立选择，形成精准匹配的工作模式。

## 📊 L1/L2/L3质量控制级别定义

> 📌 **核心概念**: 质量控制级别定义项目执行的严格程度和流程复杂度，与协作模式完全独立 

### ⚡ L1-STREAMLINED (快速迭代级)
- **核心理念**: 快速可用优于完美，聚焦核心价值最快交付
- **质量门禁**: 最小化验证点，基本功能可用即可
- **流程复杂度**: 线性流程，跳过非核心环节
- **风险承受**: 高容错，允许试错和快速调整
- **适用场景**: 快速原型、POC验证、探索性项目、学习项目

### ⚖️ L2-BALANCED (标准流程级)
- **核心理念**: 平衡质量与效率，建立可持续的标准化流程
- **质量门禁**: 标准检查点，关键节点必须验证通过
- **流程复杂度**: 模块化流程，支持并行协作和分工
- **风险承受**: 中等容错，平衡速度与质量
- **适用场景**: 商业项目、团队协作开发、标准业务应用

### 🔍 L3-RIGOROUS (严格控制级)
- **核心理念**: 质量优于速度，建立完整追溯和审计体系
- **质量门禁**: 多层验证，每个决策点都需要完整记录和审核
- **流程复杂度**: 严格状态控制，形式化流程，支持第三方审计
- **风险承受**: 低容错，优先保证系统可靠性和合规性
- **适用场景**: 关键系统、高合规项目

## 🤝 协作模式定义（对话领导权）

> 📌 **核心概念**: 协作模式定义人机对话中的领导权分配和知识贡献模式

### ✅ C1-CONFIRM模式 (AI主导型)
- **核心理念**: AI承担主导责任，基于专业知识提供最优解决方案
- **对话特征**: AI领导对话节奏，规划执行路径，承担决策责任
- **用户角色**: 需求提供者和最终确认者，专注于目标设定和结果验收
- **识别信号**: "你看着办"、"按你的经验来"、"快速完成"、"我相信你的判断"
- **适用场景**: 用户专业经验相对较少、时间紧迫、信任AI专业能力的项目
- **协作模式状态**: `SPEC_USER_COLLABORATION_MODE = "C1-CONFIRM"`

### 🤝 C2-PARTICIPATE模式 (平等协作型)
- **核心理念**: 双方作为平等合作伙伴，发挥各自专长，共同探索最佳解决方案
- **对话特征**: 双向引导，充分讨论，知识交融，共同迭代优化方案
- **用户角色**: 协作伙伴，既贡献领域知识也参与技术讨论，共同承担决策责任
- **识别信号**: "我们一起商量"、"给我建议"、"你怎么看"、"咱们讨论一下"
- **适用场景**: 复杂项目、创新性项目、需要深度定制化的项目、学习型项目
- **协作模式状态**: `SPEC_USER_COLLABORATION_MODE = "C2-PARTICIPATE"`

### 🎯 C3-LEAD模式 (用户主导型)
- **核心理念**: 用户拥有完全控制权，AI提供专业支持和执行协助
- **对话特征**: 用户控制对话节奏，主导每个决策点，掌握执行方向
- **用户角色**: 项目负责人和主要决策者，深度参与方案制定和细节把控
- **识别信号**: "我要控制细节"、"让我决定"、"按我的要求"、"我来规划路径"
- **适用场景**: 用户具有丰富专业经验、对项目有明确vision、需要精细控制的项目
- **协作模式状态**: `SPEC_USER_COLLABORATION_MODE = "C3-LEAD"`

## 📁 文档概念定义

> 📌 **核心概念**: 文档定义阶段的完整工作基础，采用三状态机制描述进展

### 文档 (Document)
**文档** = **特定阶段目录中的所有MD文件集合，构成该阶段的完整工作基础和知识载体**

> 💡 **概念区分**: 单个MD为**文件**，阶段内所有MD为**文档**

**阶段文档映射**:
- `spec/requirements/` → **需求文档** (业务需求和验收标准定义)
- `spec/design/` → **设计文档** (技术架构和系统设计)
- `spec/implementation/` → **实施文档** (TDD策略和开发计划)
- `spec/task_planning/` → **任务文档** (可执行任务和验证步骤)

### 文档状态机
文档状态机包含三种状态：
- **NOT_STARTED**: 阶段目录不存在或目录为空，表示阶段尚未开始
- **INITIALIZED**: 阶段目录存在且包含基础MD文件，但内容不完整或未达标
- **COMPLETED**: 阶段文档内容完全推敲完成，所有质量检查通过

## 🤖 AI执行视角映射（LM ↔ L）

> 定位：LM1/LM2/LM3 是对 L1/L2/L3 的执行方式视角映射，不新增决策维度

### 定义

#### **LM1-SWIFT (L1执行视角 - Vertical优先快速模式)**
**AI Coding适配**: 面向快速原型和个人项目的AI技术执行策略
1. **端到端切片优先**: AI按用户故事完整价值链生成约束，避免过度层次分解
2. **单文件聚焦**: AI专注单个约束文件生成，保持上下文清晰简单
3. **关键词导向**: AI依据"快速可用"、"基础验证"等标记控制约束复杂度
4. **快速生成**: AI快速产出约束内容，减少生成时间
5. **即时验证**: AI生成后立即自检基础完整性、格式和逻辑合理性
6. **轻量质量控制**: AI执行基础语法检查和逻辑验证，Human快速确认核心合理性

#### **LM2-FLEX (L2执行视角 - Vertical为主适度Layer模式)**
**AI Coding适配**: 面向团队协作项目的AI技术执行策略
1. **切片为主分层辅助**: AI优先端到端生成，在复杂场景下适当引入分层思考
2. **渐进式上下文**: AI逐步积累项目理解，保持约束内容连贯一致
3. **模式识别**: AI学习已有约束风格，保持团队标准化表达
4. **平衡优化**: AI在生成速度与结构化质量间找到可持续平衡点
5. **迭代完善**: AI基于反馈持续改进生成策略和内容质量
6. **协作质量控制**: AI执行交叉验证和一致性检查，Human提供业务逻辑验证

#### **LM3-STRICT (L3执行视角 - Layer优先系统化模式)**
**AI Coding适配**: 面向关键系统和审计项目的AI技术执行策略
1. **系统化分层生成**: AI按层次架构原则生成约束，确保完整体系覆盖
2. **多轮结构化**: AI通过多轮迭代构建完整的分层约束结构
3. **完整追溯**: AI记录每个约束的架构层次、决策依据和来源追溯
4. **标准化表达**: AI严格遵循格式和分层表达标准，确保一致性
5. **元数据完整**: AI为约束生成结构化描述、关联信息和验证标准
6. **严格质量控制**: AI执行多层验证和合规检查，为Human提供详细质量分析报告

### 一一映射（由 L 决定 LM）

- **L1-STREAMLINED** ↔ **LM1-SWIFT**: Vertical优先端到端，AI快速生成基础约束
- **L2-BALANCED** ↔ **LM2-FLEX**: Vertical为主适度Layer，AI平衡速度与质量  
- **L3-RIGOROUS** ↔ **LM3-STRICT**: Layer优先系统化，AI确保完整性和可追溯性
 
### 与协作模式关系
- LM/L 与 C（C1/C2/C3）可自由组合；LM 仅随 L 改变而改变。

### 用途
- 方向性自检：检查输出是否符合当前 L 对应的 LM 特征。
- 执行一致性：指导AI在不同 L 下采用匹配的实施方式与表达风格。

## 🤝 Human-in-the-loop (HITL)

> **定义**: HITL 是指 AI Agent 在高风险或低自信情形下主动暂停，邀请人类专家做出决策或授权的安全机制。

- **角色**  
  - Agent：持续执行流程，检测异常并提交结构化 HITL 请求（背景/问题/备选/影响）。  
  - Human：接收请求，给出决策或指示，并对结果负责。
- **标准触发**  
  1. 模型自信度不足或关键信息冲突。  
  2. 高影响变更（架构、进度、预算、SLA）。  
  3. 合规与审计节点需要人工签署。  
  4. 异常恢复：连续 PDCA 失败、STOP（E1）或需回滚。
- **执行要求**  
  - 触发即暂停自动执行，等待人类裁定。    
  - HITL 与协作模式（C1/C2/C3）和质量级别（L1/L2/L3）无关，任何级别都必须保留；只是 L3 相比 L1 触发更频繁、更严格。

## 📋 LLM质量控制通用原则

> **🎯 定位**: 本节定义所有阶段（REQUIREMENTS/DESIGN/IMPLEMENTATION/TASK_PLANNING）共享的LLM质量控制验收标准，避免各阶段重复定义。

### 通用质量控制检查清单

在每个阶段的门2质量门中，需验收CRAFT是否正确执行以下质量控制指令：

- [ ] **文件范围合规性**: 确认质量控制仅应用于spec/目录下非_前缀的MD文件（排除_开头的目录和文件）
- [ ] **长度控制执行验证**: 内容是否按[L1:400-500行|L2:500-600行|L3:600-800行]限制生产，超出是否提供拆分建议
- [ ] **补丁保护执行验证**: 修改后是否进行了[系统性|逻辑性|一致性]完整性检查，保护既有内容质量
- [ ] **质量预防执行验证**: 是否执行了信息密度监控、结构清晰保持、术语统一验证等预防性措施
- [ ] **阶段特异执行验证**: 是否完成了该阶段的特殊质量要求检查[需求逻辑链|架构连贯|TDD流程|任务分解]
- [ ] **人机协作触发验证**: 发现问题时是否正确触发"立即停止→Human-in-the-loop→建议审查整理修复"机制

### 各阶段引用方式

在各阶段CONSTRAINT文档的门2质量门中，使用以下简化引用：

```markdown
- [ ] **📋 LLM质量控制执行验证**: 按 CONSTRAINT_CORE_CONCEPTS.md 中"LLM质量控制通用原则"逐条验收
```
