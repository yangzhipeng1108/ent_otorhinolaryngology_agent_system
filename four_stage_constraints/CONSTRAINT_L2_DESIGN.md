## 🧪 TDD在设计阶段的正确定位

**核心原则**：可测试性设计，为TDD做准备（但不实施TDD）

```
TDD在设计阶段的职责边界：
✅ 应该做：可测试架构设计
✅ 应该做：标准测试策略规划（但不实施）
✅ 应该做：为TDD主场（实施规划）提供技术基础
❌ 不应做：编写具体测试用例
❌ 不应做：进行测试驱动开发
❌ 不应做：实施TDD的红绿重构循环
```

**价值体现**：为实施规划(Implementation)阶段（TDD真正主场）提供完整的技术架构基础

## 🎯 L2约束检查重点

### 哼将产出验收标准

> **"哼哈二将"角色分离说明**：在本框架中，CRAFT负责实际内容生产（"哼将"），CONSTRAINT负责质量检查验收（"哈将"）。本文档作为"哈将"，专门验收CRAFT生产的内容质量。

**验收CRAFT生产的设计文档符合L2-BALANCED标准：**

- **标准化验证**: 确保输出符合标准流程要求，平衡设计详实度
- **模块化架构验证**: 检查架构设计支持模块化开发，组件边界清晰
- **分层合理性验证**: 验证Vertical为主+适度Layer的分层策略
- **团队协作验证**: 检查接口契约明确，支持团队并行开发
- **技术栈平衡验证**: 验证技术选型平衡创新与稳定，主流技术组合
- **完整性检查**: 验证完整架构设计和标准技术方案完整性
- **边界合规性**: 检查避免实施TDD，保持设计阶段边界
- **格式规范性**: 验证使用完整6部分结构和标准架构图
- **技术合理性**: 检查技术选型有充分调研依据和方案对比
- **适度复杂度**: 验证架构设计平衡复杂性与可维护性
- **技术术语密度验证**: 验证技术术语密度 ≤ 20%，80%业务语言表达
- **业务上下文验证**: 检查所有技术概念都有业务理由说明
- **过程式代码禁止验证**: 确保示例不含函数调用、API方法等过程式代码
- **L2团队协作验证**: 检查技术选择有业务理由，支持团队讨论

## 📋 验收执行协议 ⭐ AI强制执行指南

> **目的**: Task-S4-4必须输出结构化验收报告，包含：验收对象清单、逐项检查结果（✅/❌+具体证据）、通过率统计、失败项详单、验收结论。
> 
> **L2特征**: 验收项比L1更多（15项）、标准更严格，需检查模块化架构、团队协作、文档数量=6。
> 
> **DESIGN特殊性**: 需验收artifacts格式、追溯链、端到端价值映射等DESIGN特有内容。

### 🔴 强制验收项（L2-BALANCED标准）- 分3组共15项

#### 第1组：格式与追溯验收（4项）

##### 1. Technical Acceptance格式验收
- 每个TAC必须包含Front Matter（id: TAC-<SN>-NNN + sn: <SN> + source_us: US-<SN>-NNN）
- TAC验收US的技术实现路径
- L2额外要求：TAC包含标准验收标准

##### 2. Function Point格式验收
- 每个FP必须包含Front Matter（id: FP-<SN>-NNN + sn: <SN> + source_us: US-<SN>-NNN）
- FP包含技术架构映射
- L2额外要求：FP包含模块接口定义

##### 3. 追溯链完整性验收
- US→TAC→FP追溯链完整
- SN字段跨文档一致
- L2额外要求：追溯关系文档化

##### 4. 文档维度完整性验收 ⭐ 新增
- **L2核心维度标准**: 必须覆盖6个核心维度
  - 维度1: Vertical Slices（端到端切片维度）- 必需
  - 维度2: Technical Acceptance（技术验收维度）- 必需
  - 维度3: Architecture（架构设计维度）- 必需
  - 维度4: API Design（接口设计维度）- 必需
  - 维度5: Data Model（数据模型维度）- 必需
  - 维度6: Component Design（组件设计维度）- 必需
- **维度覆盖验收**: 6个核心维度必须覆盖
- **检查方法**:
  - 步骤1: 确认6个核心维度必须覆盖（每个维度至少有对应文档体现）
  - 步骤2: 确认CRAFT_L2_DESIGN.md体现维度驱动原则（维度是核心，文件数量是反映）
- **失败案例**:
  - "6个vertical_slices文件" → 缺少TAC/Architecture/API/Data/Component维度覆盖
  - "3个US + 3个Architecture" → 缺少TAC/API/Data/Component维度覆盖

#### 第2组：架构质量验收（7项）

##### 6. 模块化架构验收 ⭐ L2特有
- 架构设计支持模块化开发
- 组件边界清晰，接口契约明确

##### 7. Slice优先+适度分层验收
- 以功能切片为主，适度分层
- 避免L1的平面化、避免L3的严格分层

##### 8. 技术选型合理性验收
- 基于充分调研的技术选型
- 有方案对比分析
- 平衡创新与稳定

##### 9. 可测试性设计验收
- 架构设计支持TDD（但不实施TDD）
- 为实施规划阶段提供标准技术基础

##### 10. 团队协作接口验收 ⭐ L2特有
- 接口规范具体可实施
- 支持团队并行开发
- 接口文档完整

##### 11. 技术调研充分性验收 ⭐ L2特有
- 技术选型有调研依据
- 包含方案对比分析
- 决策理由明确

##### 12. 适度复杂度验收
- 架构复杂度适中
- 平衡可维护性与完整性

#### 第3组：内容规范验收（3项）

##### 13. 端到端价值映射验收
- US的端到端价值链路（End-to-End Value Chain：前端交互/数据流转/后端处理/结果反馈）清晰
- 价值链路到架构组件的映射完整
- L2额外要求：包含主流程+关键替代路径

##### 14. 业务语言比例验收
- 技术术语密度 ≤ 20%
- 80%业务语言表达，PM能理解"做什么"
- L2额外要求：技术方案支持团队讨论

##### 15. 禁止过程式代码验收
- 示例不含函数调用（如AuthService.authenticate()、bcrypt.hash()）
- 示例不含API方法
- 允许声明式代码（接口契约、数据结构、配置文件）

## 🎯 边界约束原则

### ❌ 严禁行为
- **无需求设计**：绝不允许在没有需求文档的情况下开始设计
- **跳过技术调研**：避免直接选择技术方案而无充分调研
- **实施TDD**：不进行测试驱动开发，不编写具体测试用例

### ✅ 专注职责
- **标准架构设计**：基于需求的完整架构方案，支持模块化开发
- **技术选型评估**：平衡创新与稳定，支持主流技术栈组合
- **接口规范设计**：标准接口定义，支持团队协作开发

## 🔧 标准技术选择指导

### 标准决策矩阵
- **Web应用**: 分层架构 + 标准API + 合适数据库
- **移动应用**: 标准架构模式 + 本地存储 + 数据同步
- **数据密集**: 混合存储策略，根据数据特性选择
- **团队协作**: 模块化设计，接口契约清晰，支持并行开发

### 技术选型平衡
- **性能需求**: 评估后选择架构模式(单体/分布式)
- **团队规模**: 考虑维护复杂度与开发效率
- **业务发展**: 支持适度扩展，避免过度设计

## 🔒 质量门禁原则

### 📋 审批流程要求
```
设计文档完成后的强制流程：
1. 创建完整design/目录结构，包含标准的设计文档体系
2. 基于需求完成全面技术调研和方案对比分析
3. 必须询问："设计看起来可以吗？如果可以，我们可以继续制定实施计划。"
4. 等待明确批准（"是"、"已批准"、"看起来不错"等）
5. 如未获批准，必须修改后重新请求批准
```

### 🔄 反馈-修订循环机制
- **标准流程控制**：遵循标准设计流程，平衡深度与效率
- **持续修订**：必须根据用户反馈持续完善设计文档
- **批准标准**：只有收到正面回应才能继续

## 🚨 L2常见违规行为

### ❌ 边界违规
- 在设计中编写具体测试用例或测试代码
- 进行测试驱动开发
- 跳过技术调研直接选择技术方案

### ❌ 格式违规
- 缺少完整6部分结构中的关键部分
- 架构图不够详细或缺乏组件关系说明
- 接口设计缺少标准规范格式

### ❌ 质量违规
- 技术选型缺乏充分的调研和对比分析
- 不考虑与实施规划阶段的标准对接
- 设计复杂度过高或过低，不符合L2平衡特征

## value_path_mapping（端到端验证映射：End-to-End Verification Mapping）
