## 术语口径（中文 → English）
- 测试驱动开发（Test-Driven Development, TDD） - 先写测试后写代码的开发方法
- 行为驱动开发（Behavior-Driven Development, BDD） - 基于用户行为场景的测试方法
- 红绿重构循环（Red-Green-Refactor Cycle） - TDD核心循环：写失败测试(Red)→写代码让测试通过(Green)→优化代码(Refactor)
- Given-When-Then - BDD场景结构：前置条件(Given)→用户操作(When)→预期结果(Then)
- BDD Scenario（BDD场景） - 基于Vertical Slice转换的可执行测试场景，连接需求与实现
- 单元测试（Unit Testing） - 针对单个函数或模块的测试
- 集成测试（Integration Testing） - 验证多个模块协同工作的测试
- 端到端测试（End-to-End Testing） - 从用户视角验证完整功能流程的测试
- 测试覆盖率（Test Coverage） - 测试代码对业务代码的覆盖程度
- 技术债务（Technical Debt） - 为快速交付而暂时妥协的代码质量问题

## 🧪 TDD在实施规划阶段的L1定位

**核心原则**：⭐ TDD的快速主场 - 基础测试驱动策略制定

```
TDD在L1实施规划阶段的职责边界：
✅ 应该做：将功能设计转换为基础测试驱动的编码任务序列
✅ 应该做：制定精简的测试计划，支持快速红绿循环
✅ 应该做：为任务规划阶段提供基础TDD策略指导
✅ 应该做：核心路径测试覆盖，允许边界简化
❌ 不应做：实际执行TDD（属于任务规划阶段职责）
❌ 不应做：编写具体代码（专注于计划制定）
❌ 不应做：过度完善的测试策略设计
```

**价值体现**：为任务规划阶段提供快速可用的基础测试驱动策略方案

## 📋 验收执行协议 ⭐ AI强制执行指南

> **目的**: Task-S5-3必须输出结构化验收报告，包含：验收对象清单、逐项检查结果（✅/❌+具体证据）、通过率统计、失败项详单、验收结论。
>
> **原则**: 信任AI能力，只定义"要什么结果"，不规定"怎么做"。

> **L1分组验收原则**: L1-STREAMLINED采用"主要验收组3-4个,每组3-5个子项"模式,
> 符合`SPEC_ACA_L1_CHARTER.md`中`CheckpointCount[4-6]`的分组验收语义。
> 通过率≥95%基于总子项计算,确保质量不妥协。

### 🔴 强制验收项（L1-STREAMLINED标准）

#### 1. 项目结构内容验收
- ❌ 禁止具体文件名（Button.vue, scheduleController.js）
- ✅ 允许泛化占位符（[组件名].vue）、目录层级、关键根文件

#### 2. 测试目录位置验收
- ✅ 必须包含：单元测试、集成测试、端到端测试目录位置说明

#### 3. 文档维度完整性验收 ⭐ 新增
- **L1核心维度标准**: 必须覆盖4个核心维度
  - 维度1: Project Structure（项目结构维度）- 必需
  - 维度2: TDD Strategy（TDD策略维度）- 必需
  - 维度3: BDD Test Scenarios（BDD测试场景维度）- 必需
  - 维度4: Test Driven Sequence（测试驱动序列维度）- 必需
- **维度覆盖验收**: 4个核心维度必须覆盖
- **检查方法**:
  - 步骤1: 确认4个核心维度必须覆盖（每个维度至少有对应文档体现：Structure + Strategy + Scenarios + Sequence）
  - 步骤2: 确认CRAFT_L1_IMPLEMENTATION.md体现维度驱动原则（维度是核心，文件数量是反映）
- **失败案例**:
  - "4个bdd_scenarios文件" → 缺少Structure/Strategy/Sequence维度覆盖
  - "2个Structure + 2个Strategy" → 缺少Scenarios/Sequence维度覆盖

#### 4. Test Suite格式验收 ⭐ 新增
- **TS格式标准**: 当同一VS推导出3条以上SC场景时，引入TS-<SN>-NNN格式  
- **Front Matter检查**: TS必须包含id、sn、source_vs等标准字段
- **场景分组逻辑**: 验证TS对SC的合理分组和组织

#### 5. 快速TDD验证
- 体现"快速可用优于完美"，覆盖率60-70%，允许测试债务
- **文档长度一致性**: 控制在400-500行范围内（与CRAFT要求一致）

#### 6. Red-Green简化验证
- 可简化Refactor阶段，不要求"严格重构"

#### 7. VS测试资产完整性验收（⭐ L1核心特色）
- **VS测试资产完整性检查**（测试场景、测试数据、外部依赖、执行环境）：
  - 测试场景: 每个VS是否有对应的SC-XXX-NNN场景
  - 测试数据: BDD场景是否说明测试数据要求
  - 外部依赖: BDD场景是否说明外部依赖集成策略
  - 执行环境: 是否说明测试环境配置要求
- **VS测试资产内部完整性检查**：
  - VS的SC是否完整覆盖value_path的4个向度
  - VS测试资产是否为后续阶段提供充分基础
- **测试资产实用性检查**：
  - 测试数据要求是否具体可执行（非空泛描述）
  - 外部依赖策略是否明确具体（可实际配置）
  - 环境配置要求是否明确可验证（具体可操作）

#### 7. 高容错验证
- 允许测试债务存在，支持后续补齐

#### 8. 项目类型构建策略验收 ⭐ 新增
- **项目类型识别**: 验证是否正确识别前端/后端/全栈项目类型
- **构建顺序策略**: 检查构建顺序是否遵循项目类型的最佳实践
- **智能适配验证**: 确保策略适配项目特定需求

#### 9. 后端三层架构协同验收 ⭐ 新增
- **Phase分阶段验证**: Phase 1数据层优先 → Phase 2场景驱动的策略
- **跨层开发控制**: 验证避免跨层开发的约束机制
- **架构协同策略**: 确保三层架构与BDD场景的协同设计

#### 10. 过程式vs声明式代码区分验收 ⭐ 新增
- **过程式代码禁止**: 严格禁止函数调用、类方法、执行步骤等过程式代码
- **声明式代码允许**: 明确允许接口契约、数据结构、配置文件等声明式代码
- **区分标准验证**: 验证文档中的代码示例符合声明式原则

#### 11. 业务理由强制验收 ⭐ 新增
- **技术决策业务背景**: 每个技术决策必须说明业务理由
- **测试场景业务关联**: 验证测试场景与业务功能的明确关联
- **业务价值说明**: 确保技术实现体现业务价值导向

#### 12. 任务格式验证
- 十进制编号 + 复选框 + 四要素（任务目标、需求引用、测试要求、预期输出）

#### 13. 代码导向验证
- ❌ 禁止非编码任务（部署、培训、营销）

#### 14. 边界合规性
- ❌ 禁止具体代码实现（function、class、test()等）  
- ✅ 只包含策略性描述

## 📊 BDD Scenario格式验收标准

### BDD Scenario Front Matter验收（必填）

**Front Matter完整性验收**:
- [ ] **SC Front Matter完整性**: 每个BDD场景必须包含完整的Front Matter块（`---` 分隔符）
- [ ] **id字段**: 格式为`SC-<SN>-NNN`（如：SC-MAIN-001, SC-AUTH-002）
- [ ] **sn字段**: 业务域标识，必须与source_vs的SN一致
- [ ] **source_vs字段**: 派生来源，格式为`VS-<SN>-NNN`，引用必须有效

**验收示例（Front Matter）**:
```yaml
---
id: SC-MAIN-001
sn: MAIN
source_vs: VS-MAIN-001
---
```

### BDD Scenario内容结构验收

**Feature结构验收**:
- [ ] **Feature标题**: 直接使用Vertical Slice的用户成功状态描述
- [ ] **Background section（可选）**: 包含系统初始状态和测试前置条件

**Scenario结构验收**:
- [ ] **Scenario标题格式**: 必须标注VS ID（格式：`Scenario: [场景描述] - VS-<SN>-NNN`）
- [ ] **Given-When-Then-And结构**: 使用标准BDD格式
  - Given: 前置条件（来自VS的"前端交互"前置部分）
  - When: 用户操作（来自VS的"前端交互"操作部分）
  - And: 数据流转验证（来自VS的"数据流转"）
  - And: 后端处理验证（来自VS的"后端处理"）
  - Then: 结果反馈验证（来自VS的"结果反馈"）
  - And: 端到端一致性验证

**Value Path价值路径四向度映射验收**:
- [ ] **前端交互映射**: Given/When步骤覆盖VS的前端交互维度
- [ ] **数据流转映射**: And步骤覆盖VS的数据流转维度
- [ ] **后端处理映射**: And步骤覆盖VS的后端处理维度
- [ ] **结果反馈映射**: Then/And步骤覆盖VS的结果反馈维度
- [ ] **端到端完整性**: 包含最后的端到端一致性验证步骤

**VS追溯性验收**:
- [ ] **Scenario标题含VS ID**: 场景标题明确标注VS-<SN>-NNN
- [ ] **source_vs引用有效**: Front Matter中的source_vs引用实际存在的VS
- [ ] **SN一致性**: SC的SN与source_vs的SN必须一致

### BDD Scenario完整验收示例

**符合标准的BDD场景**:
```yaml
---
id: SC-MAIN-001
sn: MAIN
source_vs: VS-MAIN-001
---

Feature: 用户认证成功状态实现

  Background:
    Given 系统已启动并运行
    And 数据库包含测试用户"testuser"

  Scenario: 用户登录认证完整流程 - VS-MAIN-001
    # 前端交互 → Given/When
    Given 用户在登录页面
    When 用户输入用户名"testuser"和有效密码
    And 用户点击"登录"按钮

    # 数据流转 → And验证
    And 登录请求POST发送到"/auth/login"
    And 请求包含正确的credentials

    # 后端处理 → And验证
    And 后端验证用户凭据成功
    And 系统生成JWT Token

    # 结果反馈 → Then
    Then 用户收到认证成功响应
    And Token存储到浏览器LocalStorage
    And 页面自动跳转到用户Dashboard
    And 用户可以看到欢迎信息
    And 端到端认证状态在前后端保持一致
```

**验收检查点**:
- ✅ Front Matter完整（id + sn + source_vs）
- ✅ Feature标题使用用户成功状态描述
- ✅ Scenario标题含VS ID（VS-MAIN-001）
- ✅ Given-When-Then-And结构完整
- ✅ 价值路径四向度映射完整（前端交互/数据流转/后端处理/结果反馈）
- ✅ 端到端一致性验证存在

### VS→BDD转换质量验收

**转换完整性验收**:
- [ ] **用户成功状态到Feature**: Feature标题反映VS的用户成功状态
- [ ] **价值链路到Scenario**: 每个价值链路维度都有对应的BDD步骤
- [ ] **端到端价值链**: BDD场景覆盖完整的端到端价值链路
- [ ] **可执行性**: 场景描述足够具体，可直接指导TDD实现

**不合格示例（缺失价值路径四向度映射）**:
```gherkin
Scenario: 用户登录
  Given 用户在登录页
  When 用户登录
  Then 登录成功
```
**问题**: 缺少数据流转、后端处理、结果反馈的详细步骤，无法充分验证VS的完整价值链路。

## 🎯 边界约束原则

### ❌ 严禁行为
- **无设计策略**: 绝不允许在没有设计文档的情况下开始实施规划
- **实际TDD执行**: 避免编写具体测试代码或实际TDD实施
- **非编码任务**: 不包含部署、培训、营销等非编码相关任务

### ✅ 专注职责
- **基础TDD策略**: 基于设计的快速测试驱动策略制定
- **任务分解**: 将设计转换为可执行的编码任务序列
- **测试规划**: 为红绿重构循环提供基础指导

## 🔧 快速TDD策略指导

### L1测试策略矩阵
- **单元测试**: 核心业务逻辑测试，简化边界案例
- **集成测试**: 关键接口测试，主要数据流验证
- **端到端测试**: 核心用户场景，基础功能验证

### 快速测试覆盖原则
- **60-70%覆盖率**: 专注核心路径，允许边界用例简化
- **Red-Green优先**: 快速红绿循环，Refactor可后置
- **债务容忍**: 允许测试债务，通过后续迭代补齐

### ❌ 边界违规

- 跳过设计依据直接开始规划

- 追求过度完善而非快速可用

- 过度设计测试架构

**修正策略**: 快速回到L1核心原则，重新执行快速模式，确保高容错和快速可用。
