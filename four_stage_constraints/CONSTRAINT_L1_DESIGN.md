### ⚡ LLM策略要点速查
#### 🚫 严禁行为
- 绝不在没有需求文档情况下开始设计
- 不跳过技术调研直接选择方案
- 不编写具体测试用例或实施TDD
- 不过度分层，避免复杂架构设计

#### ✅ 必须规划
- 基于已批准的requirements/交付物进行设计
- **Vertical Slice优先**：端到端功能切片，跨层穿透设计
- **KISS原则**：简化架构图，核心组件聚焦，避免过度设计
- 基础研究流程：领域识别→快速调研→关键发现→来源引用
- 6部分精简结构：概述→架构→组件→数据→错误→测试
- **成熟技术栈**：优先选择稳定技术，避免复杂组合
- 必须询问："设计看起来可以吗？如果可以，我们可以继续制定实施计划。"

## 术语口径（中文 → English）
- 架构设计（Architecture Design）
- 组件接口（Component Interface）
- 数据模型（Data Model）
- 技术选型（Technology Selection）
- KISS原则（Keep It Simple, Stupid） - 保持简单直接的设计理念，避免不必要的复杂性
- C4模型（C4 Model） - 软件架构可视化框架：Context-Container-Component-Code四层次架构描述
- Function Point（功能点） - 基于Vertical Slice分解的设计单元，连接需求与架构
- Vertical Slice（垂直切片） - 端到端功能切片，跨层穿透的设计组织方式

## 🧪 TDD在设计阶段的正确定位

**核心原则**：可测试性设计，为TDD做准备（但不实施TDD）

```
TDD在设计阶段的职责边界：
✅ 应该做：可测试架构设计
✅ 应该做：基础测试策略规划（但不实施）
❌ 不应做：编写具体测试用例
❌ 不应做：进行测试驱动开发
```

**价值体现**：为实施规划(Implementation)阶段（TDD真正主场）提供基础技术架构

## 🎯 L1约束检查重点

### 哼将产出验收标准

> **"哼哈二将"角色分离说明**：在本框架中，CRAFT负责实际内容生产（"哼将"），CONSTRAINT负责质量检查验收（"哈将"）。本文档作为"哈将"，专门验收CRAFT生产的内容质量。

**验收CRAFT生产的设计文档符合L1-STREAMLINED标准：**

- **快速性验证**: 确保输出避免过度设计，符合"快速可用优于完美"原则
- **Vertical Slice验证**: 检查架构设计以端到端功能切片组织，跨层穿透
- **KISS原则验证**: 确保架构图简化，核心组件聚焦，组件内聚性高
- **技术选型验证**: 验证选择成熟稳定技术栈，避免复杂技术组合
- **完整性检查**: 验证核心架构设计和基础技术方案完整性
- **边界合规性**: 检查避免实施TDD，保持设计阶段边界
- **格式规范性**: 验证使用6部分精简结构
- **🆕 Vertical Slice承接验证**: 验证VS→TAC→FP追溯链路 (VS作为设计起点，TAC验收VS技术路径)
- **🆕 端到端价值映射验证**: 检查Vertical Slice的端到端价值链路到架构组件的映射完整性
- **🆕 端到端一致性验证**: 确认架构设计覆盖VS的完整价值链路
- **技术术语密度验证**: 验证技术术语密度 ≤ 20%，80%业务语言表达
- **业务上下文验证**: 检查所有技术概念都有业务理由说明
- **过程式代码禁止验证**: 确保示例不含函数调用、API方法等过程式代码

## 📋 验收执行协议 ⭐ AI强制执行指南

> **目的**: Task-S4-4必须输出结构化验收报告，包含：验收对象清单、逐项检查结果（✅/❌+具体证据）、通过率统计、失败项详单、验收结论。
>
> **原则**: 信任AI能力，只定义"要什么结果"，不规定"怎么做"。
>
> **DESIGN特殊性**: 需验收VS/TAC/FP格式、追溯链、端到端价值映射等DESIGN特有内容。

> **L1分组验收原则**: L1-STREAMLINED采用"主要验收组3-4个,每组3-5个子项"模式,
> 符合`SPEC_ACA_L1_CHARTER.md`中`CheckpointCount[4-6]`的分组验收语义。
> 通过率≥95%基于总子项计算,确保质量不妥协。

### 🔴 强制验收项（L1-STREAMLINED标准）- 分3组共15项

#### 第1组：格式与追溯验收（5项）

##### 1. Vertical Slice格式验收
- 每个VS必须包含Front Matter（id: VS-<SN>-NNN + sn: <SN> + source_us: US-<SN>-NNN）
- VS标题清晰描述端到端功能切片

##### 2. Technical Acceptance格式验收
- 每个TAC必须包含Front Matter（id: TAC-<SN>-NNN + sn: <SN> + source_vs: VS-<SN>-NNN）
- TAC验收VS的技术实现路径
- **TAC语义一致性检查**: TAC内容确实在验收VS的技术路径，关注性能、安全、可靠性等技术指标

##### 3. Function Point格式验收
- 每个FP必须包含Front Matter（id: FP-<SN>-NNN + sn: <SN> + source_vs: VS-<SN>-NNN）
- FP包含技术架构映射

##### 4. 追溯链完整性验收
- US→VS→TAC→FP追溯链完整
- SN字段跨文档一致

##### 5. 文档维度完整性验收 ⭐ 新增
- **L1核心维度标准**: 必须覆盖7个核心维度
  - 维度1: Vertical Slices（端到端切片维度）- 必需
  - 维度2: Technical Acceptance（技术验收维度）- 必需
  - 维度3: Function Point（功能点分解维度）- 必需
  - 维度4: Architecture（架构设计维度）- 必需
  - 维度5: API Design（接口设计维度）- 必需
  - 维度6: Data Model（数据模型维度）- 必需
  - 维度7: Component Design（组件设计维度）- 必需
- **维度覆盖验收**: 7个核心维度必须覆盖
- **检查方法**:
  - 步骤1: 确认7个核心维度必须覆盖（每个维度至少有对应文档体现：VS + TAC + FP + Architecture + API + Data + Component）
  - 步骤2: 确认CRAFT_L1_DESIGN.md体现维度驱动原则（维度是核心，文件数量是反映）
  - 步骤3: 确认追溯链完整性（US→VS→TAC→FP→COMP）
- **失败案例**:
  - "6个vertical_slices文件" → 缺少TAC/FP/Architecture/API/Data/Component维度覆盖
  - "4个VS + 2个TAC" → 缺少FP/Architecture/API/Data/Component维度覆盖
  - "VS + TAC + Architecture + API + Data + Component但无FP" → 缺少Function Point维度，追溯链断裂

#### 第2组：架构质量验收（4项）

##### 6. KISS原则验收
- 避免过度设计，架构简化清晰
- 核心组件聚焦，组件内聚性高

##### 7. Vertical Slice优先验收
- 以端到端功能切片组织架构设计
- 跨层穿透，避免过度分层

##### 8. 技术选型合理性验收
- 选择成熟稳定技术栈
- 避免复杂技术组合
- **技术决策充实度检查**: 技术选型基于充分调研，关键决策有明确依据，主要风险已识别

##### 9. 可测试性设计验收
- 架构设计支持TDD（但不实施TDD）
- 为实施规划阶段提供技术基础

#### 第3组：内容规范验收（6项）

##### 10. 受众定位验收 ⭐ 新增
- **三角受众验证**: 技术主管/架构师/PM三角受众平衡
- **理解度检查**: PM能理解"做什么"，技术主管能理解"怎么做的思路"
- **可读性验证**: 设计决策对不同角色都有适当的表达层次

##### 11. 端到端价值映射验收
- VS的价值路径四向度（Value Path Four Dimensions：前端交互/数据流转/后端处理/结果反馈）清晰
- **四向度具体映射检查**: 前端交互→前端组件设计，数据流转→API+数据模型，后端处理→业务逻辑组件，结果反馈→状态管理+反馈机制

##### 12. 业务语言比例验收
- 技术术语密度 ≤ 20%
- 80%业务语言表达，PM能理解"做什么"

##### 13. 技术内容禁止清单验收 ⭐ 新增
- **具体技术参数禁止**: JWT配置、数据库字段类型、端口号等具体参数
- **技术命令禁止**: npm命令、bash脚本、SQL语句等技术命令
- **过度技术化架构图禁止**: UML类图、时序图等过度技术化图表

##### 14. 文档引用规范验收 ⭐ 新增  
- **引用密度控制**: 每个文档≤3个引用点，每个引用≤1行描述
- **独立性验证**: 删除引用后文档仍可理解80%内容
- **引用格式检查**: 使用业务术语引用，避免技术ID

##### 15. 禁止过程式代码验收
- 示例不含函数调用（如AuthService.authenticate()）
- 示例不含API方法（如bcrypt.hash()）
- 允许声明式代码（接口契约、数据结构、配置文件）

## 📁 文件组织验收标准

### 目录结构检查（spec/design/）
- **位置验收**: 默认`spec/design/`或等效目录
- **文档数量验收**: 7个核心文档（DESIGN特殊标准，VS + TAC + FP + 架构 + API + 数据 + 组件完整设计链路与追溯链）
- **核心类目**: Vertical Slice文档、Technical Acceptance文档、Function Point文档、架构设计文档、API设计文档、数据模型文档、组件设计文档
- **命名规范**: 文件名采用lower_snake_case + `.md`
- **内容边界**: 严禁出现测试用例/TDD实施等非设计产物

### 📊 Vertical Slice格式验收

**Front Matter验收（必填元数据）**:
- [ ] **VS Front Matter完整性**: 每个VS包含完整的Front Matter块（`---` 分隔符）
- [ ] **id字段**: 格式为`VS-<SN>-NNN`（如：VS-MAIN-001, VS-AUTH-002）
- [ ] **sn字段**: 业务域标识，与source_us的SN一致
- [ ] **source_us字段**: 格式为`US-<SN>-NNN`

**内容结构验收**:
- [ ] **用户成功状态**: 清晰描述用户成功状态（从US的"So that"提炼）
- [ ] **端到端价值链路**: 包含完整路径（前端交互/数据流转/后端处理/结果反馈）
- [ ] **端到端完整性**: 价值链路覆盖完整技术栈，跨层穿透
- [ ] **MVP聚焦**: 快速原型导向，聚焦核心价值路径

**验收示例**:
```yaml
---
id: VS-AUTH-001
sn: AUTH
source_us: US-AUTH-001
---
用户成功状态: 用户登录认证成功
端到端价值链路:
  - 前端交互: 登录表单 → 提交
  - 数据流转: POST /api/auth/login
  - 后端处理: 验证凭证 → 生成Token
  - 结果反馈: 跳转Dashboard
```

### 📊 Technical Acceptance Criteria格式验收

**Front Matter验收（必填元数据）**:
- [ ] **TAC Front Matter完整性**: 每个TAC包含完整的Front Matter块（`---` 分隔符）
- [ ] **id字段**: 格式为`TAC-<SN>-NNN`（如：TAC-MAIN-001, TAC-AUTH-002）
- [ ] **sn字段**: 业务域标识，与source_vs的SN一致
- [ ] **source_vs字段**: 格式为`VS-<SN>-NNN`

**内容结构验收**:
- [ ] **Given-When-Then格式**: 使用技术视角的Given-When-Then-And结构（非用户视角）
- [ ] **技术指标明确**: 包含性能/安全/质量等可量化指标（如响应时间<500ms）
- [ ] **区别于AC**: 是技术验收（QA/架构师视角）而非业务验收（PM视角）
- [ ] **端到端链路验收**: 验收VS的完整技术实现质量
- [ ] **端到端一致性**: 包含前后端状态同步验证

**验收示例**:
```yaml
---
id: TAC-AUTH-001
sn: AUTH
source_vs: VS-AUTH-001
---
Given 认证服务启动，数据库就绪
When 用户提交登录表单
Then API响应时间 < 500ms
And JWT Token包含正确信息
And 认证失败返回明确错误
```

**AC vs TAC区别验收**:
- [ ] **AC (REQUIREMENTS)**: PM/BA定义业务验收，验证US业务需求
  - 示例: "Given 用户在登录页，When 输入正确凭证，Then 成功登录"
- [ ] **TAC (DESIGN)**: QA/架构师定义技术验收，验证VS技术质量
  - 示例: "Given 认证服务就绪，When 触发认证流程，Then API响应<500ms"

### 📊 Function Point格式验收

**Front Matter验收（必填元数据）**:
- [ ] **FP Front Matter完整性**: 每个FP包含完整的Front Matter块（`---` 分隔符）
- [ ] **id字段**: 格式为`FP-<SN>-NNN`（如：FP-MAIN-001, FP-AUTH-002）
- [ ] **sn字段**: 业务域标识，与source_vs的SN一致
- [ ] **source_vs字段**: 格式为`VS-<SN>-NNN`

**内容结构验收**:
- [ ] **name字段**: 功能点名称清晰描述
- [ ] **价值链路映射**: 包含完整映射（前端交互、数据流转、后端处理、结果反馈）
- [ ] **core_logic字段**: 核心业务逻辑简述
- [ ] **input_output字段**: 输入输出说明
- [ ] **related_us字段**（可选）: 关联User Story引用

## 🎯 边界约束原则

### ❌ 严禁行为
- **无需求设计**：绝不允许在没有需求文档的情况下开始设计
- **跳过技术调研**：避免直接选择技术方案而无调研依据
- **实施TDD**：不进行测试驱动开发，不编写测试用例

### ✅ 专注职责
- **架构设计**：基于需求的快速架构方案
- **技术选型**：成熟稳定技术栈，避免复杂组合
- **可测试性准备**：为TDD主场做基础技术准备

## 🔧 快速技术选择指导

### 快速决策原则
- **架构选择**: 简单架构优先，避免过早复杂化
- **技术栈**: 主流成熟技术，团队熟悉度优先
- **存储方案**: 适合需求的数据库方案，简化数据设计
- **接口设计**: 标准接口模式，简洁清晰

## 🔒 质量门禁审批流程

### 📋 审批流程要求
```
设计文档完成后的强制流程：
1. 创建design/目录结构，包含精简的设计文档体系
2. 基于需求完成基础技术调研和方案选择
3. 必须询问："设计看起来可以吗？如果可以，我们可以继续制定实施计划。"

5. 如未获批准，必须修改后重新请求批准
```

### 🔄 反馈-修订循环机制
- **快速迭代**：基于用户反馈快速调整设计方案
- **持续修订**：必须根据用户反馈持续完善设计文档
- **批准标准**：只有收到正面回应才能继续

## 🚨 L1常见违规行为

### ❌ 边界违规
- 在设计中编写具体测试用例
- 进行测试驱动开发
- 跳过需求依据直接开始设计

### ❌ 格式违规
- 缺少6部分精简结构中的关键部分
- 架构图过于复杂或缺失
- 技术选型缺乏调研依据

### ❌ 质量违规
- 追求过度完善而非快速可用
- 技术方案过于复杂，不符合L1快速特征
- 过度设计循环

**修正策略**: 快速回到L1核心原则，重新执行快速模式，确保高容错和快速可用。
